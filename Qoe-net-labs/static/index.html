Subjective & Objective QoE Framework for Video Conferencing under Intermittent Network Connectivity

This website runs a genuine two-participant WebRTC call and continuously samples the browser's RTCPeerConnection.getStats() API every 5 seconds to measure how RTT, jitter, packet loss, bitrate, frame rate, freezes and interruptions affect the estimated Quality of Experience. Nothing is simulated — when a metric is unavailable in your browser it is exported as an empty CSV field, never invented.

Data integrity: every number on this site is either a measured WebRTC statistic, a derived calculation from consecutive counters (documented formula), or a clearly labelled estimated QoE heuristic value. No random or fabricated telemetry is generated anywhere.

What is measured

Network

RTT (candidate-pair), inbound jitter, packet-loss % from packet counters, incoming/outgoing bitrate from byte-counter deltas, available bandwidth (congestion-controller estimate).

Audio

Inbound audio bitrate, audio packet loss, NetEq concealment events — how often the decoder had to mask missing audio.

Video

Inbound video bitrate, video packet loss, decoded FPS, dropped frames, freeze count & total freeze duration (per 5 s interval deltas).

Connectivity

Connection state, condition class (Normal / Degraded / Poor / Intermittent), interruption duration and recovery time.

Adaptive priority policy

When the measured condition degrades, the policy protects media in this order (applied for real via RTCRtpSender.setParameters() — see the log on the Conference page):

P1 · Audio

Never throttled by the policy — the Opus codec adapts by itself. Preserve speech at all costs.

P2 · Teacher video

Camera encoding is reduced (bitrate / fps / resolution) before anything else visual is dropped.

P3 · Screen sharing

First to be capped, first to be paused — on a third RTP sender of the same peer connection.

Quick start for the demonstration

  1. Open this site on two devices (or two browser windows). HTTPS/localhost is required for camera access.
  2. Enter the same Room ID on both, join, and allow camera + microphone.
  3. Press Start monitoring, accept the consent notice, and watch the live dashboard.
  4. Use the Experiments page to mark Normal / High latency / Jitter / Loss / Interruption / Recovery phases, then stop monitoring and export the CSV.

Methodology

About the project

Subjective and Objective Quality of Experience (QoE) Framework for Video Conferencing Services with Intermittent Network Connectivity — a final-year CSE research prototype.

Project details (edit for your report)

Design

One RTCPeerConnection per pair with three RTP senders: P1 microphone audio, P2 camera video, P3 optional screen-share video. The FastAPI server only relays SDP/ICE. Statistics are sampled in each browser from its own peer connection, so values describe that peer's view of the call, not the whole network.

Measured vs derived

Measured: RTT, jitter, byte/packet/frame counters, freeze and concealment counters, connection state. Derived: bitrates (Δbytes×8 / Δt), loss % (Δlost / (Δlost + Δreceived)), per-interval deltas, interruption and recovery times (5 s resolution), available bandwidth (browser congestion-controller estimate, Chromium only). Estimated: audio/video/overall quality and class — a configurable heuristic, not a subjective rating and not a machine-learning model.

Configuration in use (edit js/config.js)



Known limitations
  • Browsers cannot reliably impose packet loss or bandwidth limits on the real network; use external tools and record them on the Experiments page.
  • Metric support differs by browser: availableOutgoingBitrate, freeze and concealment counters are mainly Chromium. Unsupported values are exported as empty fields.
  • Interruption/recovery times have 5 s resolution.
  • Without a TURN server, strict NATs or firewalls can block the connection; the error is shown, not hidden.
  • The quality scores are prototype estimates and were not validated against subjective ratings.
